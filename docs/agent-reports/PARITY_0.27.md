# Phase 5 — Windows / Android parity audit for 0.27

Date: 2026-10-22. Report only; no application, package, test, version or baseline changes.

## Scope and evidence

- Windows: `sanyzrn/Nex_windows_test`, `main` at `8dbaf4c5dbd1161f13636f6a82ce8d105bd61754` (merged phase-2 cleanup). Local audit branch: `windows/0.27-parity-audit`.
- Android: `sanyzrn/DbsNex`, `release/1.80.0` at `9590194f2425ed7eb3fa46ec61c1719cb98872a4`; `apps/client/pubspec.yaml` confirms **2.1.15**. This is a pinned comparison, not a comparison with today's Android main.
- Method: inspect actual screens, controllers, widgets, module rollout and shared-package diffs; scan all **138 Dart files** under Windows `apps/desktop/lib`; inspect two existing Windows review images: `b8_cycle_wide_fa_light.png` and `b8_vault_compact_en_light.png`. These are stored baselines, not new screenshots or proof of current execution.
- Environment: Linux; Flutter, Dart and PowerShell unavailable. Neither app was launched. Visual differences below describe source-defined layout and the two existing Windows images; live motion, pixel parity, focus, accessibility and Windows integration remain **not run**.
- S = a bounded change in a few desktop files; M = a complete interaction across several files; L = a feature/port requiring its own design and validation. These are scope estimates, not time promises. Risk is the likely implementation risk, not a claim of a demonstrated crash.
- No complete package sync is proposed: Windows has deliberate card, board, theme and workspace extensions. Replacing `packages/ui` with Android's copy would remove desktop APIs.

## Decision: five small candidates, in value order

Only the owner-selected candidates enter phase 6. No candidate below has been implemented.

| ID | Candidate | Why / bounded acceptance | Size | Risk |
|---|---|---|---|---|
| P1 | Make bulk Pin/Unpin consistent | A mixed selection currently toggles every item individually. Match Android: pin every unpinned item; unpin only when all selected items are pinned. Reflect the action in the tooltip. Check mixed/all/none-pinned selections and repository pin limits; never silently unpin an already-pinned item in a mixed selection. | S | Low–medium: changes note state, although existing commands suffice. |
| P2 | Add an existing-tag chooser in note detail | Keep creating tags, but also offer searchable existing tags with their colors and exclude tags already on the note. Start with one note; bulk tagging is a separate future decision. Reuse existing `tags` / `tag` commands; do not change persistence. | M | Low–medium: async refresh, duplicate selection and narrow layouts. |
| P3 | Expose date presets in Library search | Add Any time / Today / Last 7 days / Last 30 days and clear-state handling. Existing `SearchFilters.createdFrom/createdTo` already travel through the worker into SQL. Verify combinations with query/type/tag/thread and local midnight converted to UTC. No schema or new saved setting is needed. | M | Medium: timezone boundaries and filter reset behavior. |
| P4 | Use the existing Nex dialog shell for three Cycle dialogs | Limit the first step to period edit, period delete and typical-length settings in `cycle_view.dart`. Use the already-vendored `NexAlertDialog`; retain their current route, validation, focus and return values. This improves the glass shell without introducing Android's route machinery or a whole-app migration. | S | Low–medium: presentation changes need Windows visual review; the wrapper can look unchanged with glass disabled. |
| P5 | Normalize ordinary Library copy notices | Route the three copy paths in `library_actions.dart`, `library_keys.dart` and `library_list_pane.dart` through the existing `showNexNotice` helper. Check rapid repeats, replacement, expiry and close behavior. Keep deletion/attachment Undo and private clipboard behavior out of this first step. This improves consistency; it does not claim Android capsule parity. | S | Low: message timing/presentation; existing localization can be reused. |

P1 evidence: Windows `library_list_pane.dart:60–79` vs Android `timeline_selection.dart`, `_pinSelected`. P2: Windows `note_detail_view.dart:472–485` vs Android `widgets/tag_picker.dart` and `timeline_note_actions.dart`. P3: Windows `library_view.dart:145–159`, `store.dart:309–342`, repository `_filterClause`; Android `note_search.dart` and `search_filter_sheet.dart`. P4/P5: the widget inventory and paths below.

For every selected item, phase 6 must cover Persian/English, light/dark and RTL/LTR on the changed screens, extend the relevant behavior test and run applicable CI checks. Any changed pixels must be declared for Windows-runner baseline review; do not regenerate or loosen golden baselines locally.

## Area-by-area findings

Paths beginning with `nex/`, `ui/` or `updates/` below are relative to Windows `apps/desktop/lib`. Android paths are relative to `apps/client/lib` unless a package is explicitly named. “Keep” is a desktop adaptation, not an unfinished parity task.

| Area | What exists and what Windows lacks | Look / interaction difference | Scope / risk | Desktop fit |
|---|---|---|---|---|
| Navigation and main layout | Windows has panel/window modes, nav rails, command palette and a resizable list/detail split. Android uses timeline/tools and modal navigation. | Windows opens a second reader pane at widths >=900; Android's phone flow is primarily one screen/sheet at a time. | L / high to force equivalence. | **Keep** desktop navigation, Ctrl+K and two-pane reading. Do not port the phone dock wholesale. |
| Popup and context menus | Shared popup helpers already landed in 0.26. Five `NexPopupMenuButton` sites and one `nexShowContextMenu` remain; the single stock tag row is an intentional colored-dot exception. | Windows note context menu exposes Open, Pin, Copy, Remind and Delete; Android's configurable hold menu includes selection and card expansion, and supports a keyboard menu trigger. Windows uses a secondary pointer callback. | M / medium for action/keyboard parity. | Keep right-click. Add only useful missing actions after selection semantics are settled; do not reimplement the completed popup sync. |
| Dialogs / sheets | Windows still constructs 23 `AlertDialog`s and 27 `showDialog` calls; zero app-level `NexAlertDialog`s. Android uses `nexShowDialog`, `nexShowSheet`, `NexDialogBody` and the shared alert shell. | Shared colors/radii already theme Material dialogs. Android additionally has its own entry/exit motion and glass wrapper; desktop uses centered dialogs, with module dialogs capped at width 1040. | S for P4; M–L / medium for all routes. | Centered dialogs suit desktop. Keep Escape, keyboard traversal and panel holds; swipe handles/phone dismissal gestures are unnecessary. |
| Note cards and footer | Windows uses the shared `NoteCard`, with desktop-owned board, active-reader state, tag tint and checklist interaction extensions. The pinned Android card has a separate footnote with attachment counts, compact/full reminder wording and timeline connector options. Its expansion menu measures whether more content is available. | Android's card/footer composition differs substantially from the vendored Windows fork. Windows has board cells and inline checklist toggles that the Android constructor does not expose. | L / high for sync. | Selective adaptation only, with a documented package sync if needed. Never replace the file to obtain the newer footer. No clipping bug was reproduced here. |
| Other cards / surfaces | Seven raw `Card` constructors remain: attachment rows, AI action, Cycle overview/calendar/history, PDF empty state and Vault rows. Shared desktop `NexSoftCard`/`NexFeatureCard`/`NexWorkspaceCard` are used elsewhere. | Material cards already inherit a zero-elevation Nex card theme. The difference is wrapper treatment and content composition, not “seven unstyled cards.” | S–M / low–medium per screen. | Unify deliberately by screen; retain PDF viewer layout and private-content boundaries. |
| In-app banners / notices | Android has an overlay capsule with done/failed/AI kinds, replacement and optional action. Windows has 13 `SnackBar` construction sites; only one is the common `showNexNotice` implementation, and 12 bypass it. | Both use branded styling; Android's capsule arrives at the top with motion. Windows uses themed floating SnackBars at the bottom, with differing per-call timeout/close policies. | S for P5; M / medium for a new banner host. | First normalize behavior. A desktop overlay is optional and needs keyboard, reduced-motion, text-scale and Undo checks. Do not confuse these with OS toasts. |
| Buttons, switches and dropdowns | Filled/outlined/text/icon buttons already use shared theme tokens; desktop has focus-ring/accessibility helpers. Seven standalone `Switch` and six `SwitchListTile` sites remain; no direct `NexSwitch` use. Eighteen dropdowns use Nex radius/surface helpers. | Android uses shared switch rows and touch-friendly sheets; Windows retains keyboard-friendly form dropdowns and compact toolbars. | S–M / medium for replacement. | Keep desktop form validation and keyboard operation. Count alone is not a reason to replace a control. |
| Settings discovery / appearance | Windows already has searchable category cards, Persian text folding, language, light/dark/system, palettes/accent, text scale, density and Solar calendar. Android can filter individual settings rows via `_searchTextOf`. | A Windows search narrows categories through curated keywords, then opens a whole category. Android's search is finer grained. Category layout is a deliberate desktop presentation. | M / medium for row-level search. | Useful later; **settings search is not missing**. Startup, monitor, hotkey and panel geometry settings remain desktop-specific. |
| Library search / filters | Windows has debounced FTS/query operators, type, tag, thread, trash, stale-response guards and retry UI. Its controls hold one type and one tag. Android supports multi-tag/multi-type selection and date presets, plus integrated semantic results / nearest-miss state. Windows semantic search lives separately in the assistant workspace. | Windows horizontal filter menus vs Android's persistent multi-choice filter sheet. | M / medium for P3; L / medium–high for a full unified search experience. | Date presets are a useful small step. Multi-select and semantic integration should be separate decisions. Do not label semantic search globally absent. |
| Note tagging / threads | Windows note detail removes tag chips, accepts a typed tag name, creates threads and joins existing threads. No existing-tag chooser is presented there. Android has `TagPickerSheet` and reusable thread pickers. | Typing an exact tag name is less discoverable than selecting an existing colored tag. Windows thread dropdown is already functional. | M / low–medium for P2. | Reuse existing data commands and colors; no need to port the phone sheet itself. |
| Multi-selection / bulk actions | Windows Ctrl/Shift click toggles membership and shows Pin, Copy and Delete/Undo. Android offers Tag, Thread, Pin, Share, Copy and Delete. Windows mixed-selection Pin toggles each note; Android chooses one batch intent. | Windows Shift currently toggles one note rather than selecting a contiguous range. Android selection starts from the hold menu. | S for P1; M / medium for batch tag/thread or range selection. | Fix P1 first. More bulk actions are useful but must fit the narrow panel. Native share semantics need a separate design. |
| Reminder picker and delivery | Windows already supports quick times, custom Solar/Gregorian date + 24h time, once/daily/weekly, clear, future validation and delivery failures. Android uses `ReminderWheel` in the shared sheet and reports relative scheduled time after saving. | Desktop dialog/chips/form-field vs phone wheel/sheet; Windows closes after successful save rather than using Android's success banner. OS delivery uses Windows scheduling rather than Android permissions/alarms. | S–M / medium for UI feedback; L / high for scheduling changes. | Keep Windows scheduler, recurrence/receipt handling and notification identity. Actual delivery, sleep/time changes and system settings remain Windows checks. |
| Capture / editing | Windows already captures text/checklist/link, imports image/audio/files, records audio and supports clipboard image/text. Android additionally has camera/share intake, photo crop/annotation and phone gesture affordances. | Desktop actions/shortcuts and persistent editor vs phone capture sheet and media editing screens. | L / medium–high for an image editor. | File import, clipboard and shortcuts suit desktop. Camera, haptics, Quick Settings tiles and Android share-receiver UI do not need literal ports. |
| Media / documents in note detail | Windows displays photo notes and audio controls; generic file notes show identity and can open with the OS or the PDF module. Android has tap-to-expand photo viewing, inline video, PDF, DOCX/text previews and crop/annotation flows. | Windows PDF is a separate module/dialog; file attachments are rows. Android embeds richer readers in note details. | L / medium–high for full parity. | Inline image/PDF/document previews can be valuable future work; a video backend and document reader should be scoped separately. No playback performance claims were tested. |
| AI / smart summary | Windows has cloud provider/model settings, note actions, assistant, semantic search, a brief and writing portrait. Its brief already has a source fingerprint, >=1h success interval and 15m retry interval; Android has corresponding brief policy. | Windows assistant is a workspace; Android uses chat/note sheets. Android also has its own on-device integration. | L / high for on-device runtime or workspace replacement. | Keep the desktop workspace and existing refresh rules. Local runtime is not a small UI parity task. Provider behavior was not exercised. |
| Privacy / locking | Windows Vault/Cycle have a shared Windows Hello private session, two-minute idle grace, focus hiding and protected private clipboard. Android has app-wide lock preferences and private-tool flows. No corresponding general-library app-lock control was found in desktop settings/shell. | Platform-authentication and lifecycle boundaries differ. Existing Windows private locking is present, not missing. | L / high for app-wide locking. | A full app lock can make sense, but needs a separate threat/lifecycle design; preserve Hello, private-session teardown and storage keys. |
| Backup / import / updates | Windows has notes/full archive UI, recovery/import, release notes and verified desktop updates; Android has phone-specific backup and updater screens. | Desktop uses file pickers and installer handoff rather than phone destinations/update flow. | L / high if formats or update verification change. | Keep host-specific UI. Archive interoperability belongs to phase 4 and is **not verified by this audit**. Update identity/verification is outside phase 5. |
| Onboarding / help / platform extras | Windows has welcome choices, first-run library actions, shortcuts help, utility tools, startup and panel management. Android also exposes profile, widget settings, sponsor cards and phone settings. | Profile/avatar and touch tours are not the same information architecture as a Windows utility workspace. | M–L / medium, depending on feature. | Keep relevant desktop help; phone widgets, haptics, app-icon switching and sponsor placement are product choices, not automatic desktop requirements. |
